# Experiment Review: Checkout redesign

Generated by AB Advisor as an example of how to write up a Bayesian test for an exec / product review. Numbers below match `python -m src.cli data/sample_experiment.csv` on the bundled sample (seed 42).

## Decision

**Ship the treatment.**

Primary metrics (conversion, revenue per user) show a high probability of a useful improvement. Guardrail bounce is not signaling material harm. Secondary metrics (time on page, event counts) are compatible with no meaningful change.

## Design snapshot

- Control vs treatment, intended 50/50 (SRM p = 1.0 — split is exact)
- n = 5,000 users per arm
- Primary: `converted`, `revenue`
- Guardrail: `bounce` (lower is better)
- Secondary: `time_on_page_sec`, `events_count`
- 90% highest-density credible intervals
- MDE = 2% relative; ROPE = ±1%
- Conversion prior: Beta(1, 1) (uniform — we did not lean on last-quarter history)

## Results (from the engine)

| Metric | Control | Treatment | P(better) | Expected lift | 90% HDI |
|---|---:|---:|---:|---:|---|
| converted | 9.86% | 12.94% | 100% | +31.4% | [+19.7%, +43.8%] |
| revenue (ARPU) | $5.39 | $7.56 | 100% | +40.8% | [+26.3%, +55.6%] |
| time_on_page_sec | 179.7s | 179.9s | 58% | +0.1% | [−0.6%, +0.8%] |
| events_count | 3.03 | 3.08 | 93% | +1.7% | [−0.2%, +3.6%] |
| bounce | 41.6% | 40.3% | 9.7% *higher* | −3.1% | [−7.1%, +0.6%] |

P(better) is P(treatment mean > control mean). For bounce, *lower is better*, so 9.7% chance of an increase is the same as a ~90% chance bounce improved. That is not a ship bar on its own; it is enough to say the guardrail is not on fire.

Revenue is modeled as a **hurdle**: P(purchase) × E[spend | purchase]. Both pieces moved with conversion, so ARPU is not a mirage of a few whales.

Time on page is a textbook null: the 90% HDI includes zero and the ROPE. Events are a maybe; we do not save or kill the experiment on them.

## What we will do next

1. Ramp to 100% with a 5% holdout for one week in case of a novelty effect.
2. Watch payment-error rate and p95 checkout latency (not in this CSV) on the same dashboard.
3. Record the prior, MDE, and 95% P(better) bar in the experiment ticket so the next test cannot quietly move the goalposts.

## What this is not

- It is not “p < 0.05.” A frequentist z-test on conversion is ~10⁻⁶ here; we still would not use that language in the review.
- It does not prove the copy caused the lift if assignment was broken. SRM on this file is compatible with 50/50.
- It assumes users are independent. If the new checkout changes inventory for everyone, this model is the wrong tool.

## Talking track (90 seconds)

> We ran a 10k-user checkout test. There is effectively a 100% chance the new flow converts better than the old one, with an expected +31% relative lift. The 90% interval is roughly +20% to +44% — it does not include zero. Revenue per user follows conversion; we are not buying conversion with discounts. Time on page did not move. Bounce ticked down, not up. I recommend shipping, keeping a small holdout, and locking this same decision bar for the next experiment.
